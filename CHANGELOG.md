# Changelog

## [Unreleased]

### Fixed

- `lfmap jobs register` writes the full path of `pwsh` into each task (`--pwsh` overrides). With PowerShell from the Microsoft Store, Task Scheduler could not start `pwsh` by name, so every job failed with `0x80070002`, even at the lock screen. `lfmap jobs doctor` gains a `pwsh` check that also flags tasks registered with plain `pwsh`.

### Added

- `lfmap-knowledge` search and query operations (TC-K10, TC-K11): all seven operations are now wired into `tool.py`. New `search.py`: `search` ranks chunks with FTS (`keyword`), cosine (`vector`) or reciprocal rank fusion of both (`hybrid`, `RRF_K = 60`); `hybrid` falls back to keyword when Ollama or the vector store is missing, `vector` reports `backend_unavailable`. Chunks map to their indexed files sorted by relative path (the rest go to `duplicates`); stale vector hits whose chunk is gone are dropped. `get_context` packs up to 20 hybrid hits into `token_budget` (about 3 characters per token, only the first chunk is ever cut) with citations. On `mcp` and `rest`, `secret` roots never appear in results, duplicates, related files or root filters, and neither do roots that the current config marks `secret` or no longer lists (so they are hidden before the next reindex); every `search`/`get_context` call that returns text there writes one `egress_log` row (UTF-8 bytes). `search_files`, `get_file`, `search`, `get_context` and `related` pass every caller path through `require_read`. Now public: `catalog.root_id`, `catalog.after_ns`, `indexer.vector_store`, `indexer.data_dir_of`, `indexer.root_sensitivity`. `catalog.get_file` and `edges.related` raise `not_found` for a file in an excluded root; `edges` uses `catalog.abs_path`.
- `lfmap-knowledge` incremental reindex and status (TC-K9, `indexer.py`), wired into `tool.py` as the `reindex` and `status` operations (the other five stay not implemented until K10 + K11). `reindex` follows spec section 4 under `indexer.lock`: syncs the `roots` table and per-root `sensitivity`, scans only folders that exist (a missing root folder counts as an error and deletes nothing), extracts pending files (one content per hash, three attempts before `error`), writes chunks, FTS and edges, garbage-collects orphaned contents and embeds with Ollama. Ollama being down is not an error: `embed_skipped_reason` says why and keyword search still works. A deleted `vectors/` folder is re-embedded; `full` rebuilds from the Markdown cache; a new extractor version re-extracts. `status` uses a read-only connection and never holds the lock. Temporary: on the `cli` channel progress lines `"<stage> <done>/<total>"` go to stderr, so `--json` stdout stays clean, until core has a progress hook.
- `lfmap-knowledge` file catalog queries (TC-K12, `catalog.py`): `search_files` by name words (accents and case ignored), root, extension, status and `modified_after`, newest first; `get_file` with chunk count, live duplicates and Markdown cache flag; `exclude_root_ids` hides `secret` roots from both. Differs from the spec, following the merged K1 schemas: there is no `glob` field, so a `query` containing `*`, `?` or `[` is a glob on the relative path; `get_file` returns no edges (they come from `related`, TC-K13). Not yet wired into `tool.py` (K10 + K11).
- `lfmap-knowledge` edges (TC-K13): `edges.link_generated_from` links `X.md` to `X` or `X.<ext>` in the same folder, `edges.link_references` stores relative Markdown links that resolve inside the same root (link paths are strings only: UNC, absolute, drive-letter and scheme links are dropped, also after percent-decoding), and `edges.related` returns related files with reason `duplicate`, `generated_from`, `references`, `referenced_by`, `similar_content` (mean chunk vector, skipped when there are no vectors) or `same_folder`, hiding deleted files and `exclude_root_ids`. Not yet wired into `tool.py`.
- `lfmap-knowledge` vector store (TC-K8): `vectors.LanceVectorStore`, one LanceDB table per embedding model (`model_slug`) under `vectors/`, opened lazily; upsert by `chunk_id`, cosine search, delete by content hash (validated before the filter), `vector_of`, `drop` and `optimize`, which builds an `IVF_HNSW_SQ` cosine index from 50,000 vectors.
- `lfmap jobs doctor [--json]` (Roadmap 1.8, TC-J4): read-only checks for uv, `jobs.toml`, the tasks in `\LFMAP\`, their logon type and wake setting, sleep on AC power and, when an enabled job uses a plugin with network access, Ollama. Exit 1 when a check fails. A task that runs only while you are logged on is a warning, not a failure. See `docs/jobs.md`.
- Job channel and approval queue (Roadmap 1.8, TC-J3). `lfmap jobs run` lets T0 run, and T1 too when `max_tier = 1`. It queues every other call as a proposal in `%LOCALAPPDATA%\lfmap\approvals\pending\`, and identical pending proposals are reused. Jobs never ask, and they ignore grants, pre-approvals and preapproved destinations. A policy `deny` is refused, not queued. `lfmap approvals pending`, `approve <id>` and `reject <id>`: approve and reject need an interactive terminal and are not exposed over MCP. Approve runs the proposal once, with no reads outside the roots, and asks again above its tier. Proposals expire after `[jobs] approval_ttl_days` (default 7). Files only move between `pending`, `done`, `rejected` and `expired`.
- Scheduled jobs (Roadmap 1.8, ADR-018, TC-J1 and TC-J2): `%LOCALAPPDATA%\lfmap\jobs.toml` (`LFMAP_JOBS` overrides) declares jobs with a daily, weekly or every-N-minutes schedule. `lfmap jobs list`, `lfmap jobs run <id>` (channel `job`) and `lfmap jobs register [--dry-run]`, which creates or deletes Windows Task Scheduler tasks in `\LFMAP\` only. `scripts/Invoke-LfmapJob.ps1` runs a job, keeps its exit code and appends a line to `%LOCALAPPDATA%\lfmap\logs\jobs-YYYY-MM-DD.jsonl`. See `docs/jobs.md`.
- Claude Code cloud sessions run `uv sync` at start (`.claude/hooks/session-start.sh`); the hook does nothing on local machines.
- `lfmap-knowledge` pure modules TC-K4 to TC-K7: `extract` (markitdown call, Markdown cache by content hash with atomic writes), `chunker` (heading-aware chunks with source offsets, tables kept whole or split with a repeated header), `fts` (Vietnamese folding, FTS5 keyword search) and `embed` (Ollama embedder, loopback URLs only, environment proxies ignored). K4, K6 and K7 were written by the local qwen loop and reviewed; K5 was written in review.

- `lfmap-core` version 0.2.0: user config, risk-tiered approvals, audit log, grants and the plugin context fields listed below (Phase 1 prerequisites TC-C1 to TC-C5).

- `lfmap-core` 0.1.0: `Tool`, `@operation`, `invoke`, `ToolError`, `lfmap.toml` manifest schema and loader, entry-point discovery (`Registry`), Permission Manager (`fs_read`, `fs_write`, `network`; network paths refused).
- Generated CLI (`lfmap plugins list`, `lfmap <plugin> <operation>`, `--json`, confirmation for operations with side effects) and MCP adapter (`lfmap serve mcp`, tools named `<plugin>_<operation>`).
- Reference plugin `lfmap-echo` with operation `say`.

- `lfmap serve mcp --approve <plugin>.<operation>`; MCP tools carry read-only and open-world hints.
- `ToolContext` carries the plugin's `data_dir`, `temp_dir`, `settings` (from `[plugins.<id>.settings]` in the user config), the calling `channel` and an `approver` hook. `context_for` builds the context for an in-process call to another plugin with no more rights than the caller.
- `lfmap_core.approval`: risk tiers T0–T3 (ADR-017), the `[approval]` policy in `config.toml`, the approval decision table and an append-only `audit.jsonl`. T3 can never be pre-approved or relaxed below "ask", and only an interactive CLI may ask for it. Wired into the CLI and MCP adapters (see Changed).
- Interactive CLI reads (TC-C1, TC-C3): a path a person types at an interactive terminal may be read outside the configured roots; each such read writes a `read_outside_roots` audit line. Network and device paths are still refused, writes never widen, and MCP or non-interactive CLI calls stay inside the roots.
- `lfmap plugins health`, `lfmap config path` (config file and each plugin's expanded read/write roots), `lfmap config add-folder FOLDER --as documents|exports|knowledge` (interactive terminal only, network paths refused, edits one line so comments stay, audited) and `lfmap audit tail [-n N] [--json]` (TC-C5).
- Preapproved T3 destinations (ADR-017): `[approval.destinations."host"]` in `config.toml` with `data = "normal" | "private"` and `expires` (a date at most 90 days ahead). A plugin passes `destination` and `data` to `ctx.require_approval("external", ...)`; an unexpired destination that may receive that data level allows the call, which is audited. Secret data never matches, and a policy `deny` still wins. Operations declared `side_effects = "external"` are still gated before they run, so they still need a grant or an interactive terminal.
- `ToolContext.require_approval(reason, detail)` lets a plugin escalate a call to T2 (overwrite, rename, delete) or T3 (`external`) before acting.

### Changed

- CLI and MCP decide approvals by tier (ADR-017). Operations declared `local_write` (T1) now run without a prompt and are logged to `audit.jsonl`. T2 asks: a terminal prompt or `--yes` in the CLI; `serve mcp --approve` (now valid for 8 hours) or MCP elicitation. T3 needs a grant, or a prompt in an interactive terminal; `--yes`, `--approve` and elicitation never cover it. A connection that cannot carry elicitation is refused, not allowed.
- CLI and MCP now expand permission variables from the user config instead of none. A list variable gives one root per entry; an undefined variable grants nothing (with a warning) instead of failing the whole plugin. Relative roots are refused, and so is a root that resolves to a network path.

### Security

- MCP refuses operations with side effects unless the user approved them with `--approve` when starting the server (ADR-009). Operations with `external` side effects cannot be pre-approved.
